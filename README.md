## Варианты архитектуры

### Вариант 1: Полностью локальный стек
#### Состав
- LLM: локальная модель (например, Qwen3-4B), развернутая на собственном GPU-сервере. 
- Эмбеддинги: локальная модель (например, all-MiniLM-L6-v2) через SentenceTransformers.
- Векторное хранилище: ChromaDB.

#### Как работает
Все компоненты развернуты на серверах компании. Документы загружаются через корпоративный коннектор, разбиваются на чанки (256–512 токенов), эмбеддинги вычисляются локально, сохраняются в ChromaDB. Запросы обрабатываются по следующей цепочке: поиск в ChromaDB -> релевантные чанки -> промпт -> локальная LLM -> ответ.

#### Плюсы
- Данные не покидают периметр компании, для корпоративной базы знаний это критически важно.
- Модели можно менять без переиндексации всех документов (при совместимой размерности), ChromaDB - open-source.
- Нет операционных расходов на токены.
- Преимущества ChromaDB - встроенная персистентность, метаданные-фильтры.

#### Минусы
- Требуется своя инфраструктура - для ~25000 документов и 400 новых в месяц нужен сервер с GPU (минимум 24 GB VRAM для комфортной работы).
- ChromaDB имеет ограничения по масштабируемости - производительность падает после ~200k векторов. С учетом текущего объема данных запас остается очень небольшой.
- Обновление моделей, бэкапы, мониторинг - все должно быть реализовано силами команды.

#### Когда подходит
Если компания запрещает вывод данных за периметр, есть GPU-сервер и команда готова поддерживать инфраструктуру.

### Вариант 2: Гибрид
#### Состав
- LLM: облачная модель OpenAI / YandexGPT.
- Эмбеддинги: локальная модель (all-MiniLM-L6-v2) на CPU-сервере.
- Векторное хранилище: FAISS с собственной оберткой для персистентности и метаданных.

#### Как работает
Документы разбиваются на чанки, эмбеддинги вычисляются локально на CPU, сохраняются в FAISS. Запросы обрабатываются по следующей цепочке: локальный эмбеддинг запроса -> поиск в FAISS -> обработка метаданных и фильтрация на стороне приложения -> промпт -> вызов LLM API -> ответ.

#### Плюсы
- Высокая производительность поиска
- Не нужен GPU для эмбеддингов, достаточно CPU, не нужен сервер для LLM.
- Гибкость в выборе LLM - облачную модель можно заменить.

#### Минусы
- У FAISS нет встроенного CRUD, персистентности, метаданных и фильтров, их придется реализовать самостоятельно.
- Т.к. LLM облачная, запросы и контекст уходят за периметр.
- Если API изменится или подорожает, придется мигрировать на другую LLM.

#### Когда подходит
Если нет GPU, но нужна высокая скорость поиска и компания готова использовать облачную LLM. Подходит для пилота или MVP.

### Вариант 3: Облачный стек
#### Состав
- LLM: облачная модель OpenAI / YandexGPT.
- Эмбеддинги: облачный OpenAI
- Векторное хранилище: Qdrant

#### Как работает
Документы загружаются в облачное хранилище, разбиваются на чанки, эмбеддинги вычисляются через API, сохраняются в Qdrant. Запросы обрабатываются по следующей цепочке: эмбеддинг запроса через API -> поиск в Qdrant -> промпт -> LLM API -> ответ.

#### Плюсы
- Развертывание, обновления, бэкапы и масштабирование выполняются на стороне провайдера.   
- При росте объемов данных не придется менять архитектуру.

#### Минусы
- Данные и запросы уходят в облако.
- Завязка на проприетарные эмбеддинги, поменять модель может быть проблематично.
- Значительные операционные расходы (плата за API эмбеддингов, LLM-токены, БД)
- Зависимость от провайдера.

#### Когда подходит
Если приоритет - скорость запуска и минимальные требования к команде, а облачная обработка данных допустима политикой компании.

### Итоговое решение
Данные, по которым требуется реализовать поиск (модели промышленных объектов, архитектурные решения, регламенты, бизнес-правила и т.п.), явно не должны покидать периметр компании. Масштаб компании (9 лет на рынке, крупные заказчики, промышленный профиль) дает основания предполагать, что бюджет на свою GPU-инфрастуктуру найдется. Используем вариант 1 - полностью локальный стек.
